# WorkBench repo map (branch `bangla-eval`, read-only survey 2026-10-04)

Repo root `WorkBench/`. All paths below are relative to it. **All data paths in code are cwd-relative** (`src/tools/state.py:6-13`, `src/evals/inference.py:290`, `src/evals/metrics.py:21`, `.env` at `src/cli.py:21`), so run every command from the `WorkBench/` root.

## 1. Data layout
- **Task CSVs**: `data/processed/tasks_and_outcomes/{domain}_tasks_and_outcomes.csv`, domains = `email`(90), `calendar`(110), `analytics`(120), `project_management`(80), `customer_relationship_manager`(80), `multi_domain`(210) = **690 tasks**. Task text is unique within each file.
- **Columns**: `task`, `outcome` (Python-literal list of call strings, e.g. `['email.delete_email.func(email_id="00000479")']`, parsed with `ast.literal_eval`), `base_template`, `chosen_template`, `domains` (Python-literal list).
- **Versions** (`src/evals/metrics.py:21-82`): `CURRENT_GROUND_TRUTH_VERSION = "v2"` = the **top-level files (current)**. Subdirs are frozen snapshots: `v1/` = pre-correction GT used by the March 2024 paper runs; `v2026-05-17/` and `v2026-05-19/` = intermediate 2026 snapshots used only by the 12 committed `qwen-3.5-flash_domains_2026-05-17*` and `deepseek-v4-pro_domains_2026-05-19*` runs. All versions are row-aligned with the same shape. Task wording differs between versions (v1 vs v2: 56 tasks per README; v2026-05-17 vs v2: 39 tasks), and some outcomes differ too.
- **Templates (69 base templates)**: dict lists in `scripts/data_generation/task_outcome_generation/`: `generate_analytics_*.py:270 ANALYTICS_TEMPLATES`(12), `generate_calendar_*.py:277 CALENDAR_TEMPLATES`(11), `generate_email_*.py:190 EMAIL_TEMPLATES`(9), `generate_project_management_*.py:189 PROJECT_MANAGEMENT_TEMPLATES`(8), `generate_customer_relationship_manager_*.py:170 CRM_TEMPLATES`(8), `generate_multi_domain_*.py:556 MULTI_DOMAIN_TEMPLATES`(21). Each dict has keys `task`, `alternative_tasks`, `logic` (fn → format kwargs + `outcome`), and `domains`.
- **Generation**: `workbench-generate-data --force` (`src/cli.py:161`) regenerates the sandbox DBs and then all task files. The core is `src/data_generation/data_generation_utils.py:217-275`: seeds 42, randomly picks base or alternative wording, `.format(**logic)`, makes up to 10 unique tasks per template, and writes with `QUOTE_ALL`. **It overwrites the top-level GT. Don't run it.**
- **Sandbox DBs** (loaded once per process, then copied per thread, `state.py`): `data/processed/{calendar_events(300),emails(500),analytics_data(1000),project_tasks(300),customer_relationship_manager_data(200)}.csv`, plus `data/raw/email_addresses.csv` (directory). Fixed "now" = `HARDCODED_CURRENT_TIME = 2023-11-30T00:00:00` (`data_generation_utils.py:10`).

## 2. Inference (`workbench-inference` → `src/cli.py:17 inference()` → `src/evals/inference.py:252 generate_results`)
- **Flags**: `--model_name` (required, must be a `MODEL_REGISTRY` key), `--tasks_path` (required), `--tool_selection` (default `all`; or `domains`), `--workers` (default **64**), `--log_traces`, `--act_without_confirmation`, `--structured_outputs`, `--resume` (all boolean flags). The batch wrapper `scripts/inference/generate_all_results.py` takes `--models/--tool_selections/--task_paths` with the same flags. The committed 2026 "Revisited" runs all used `structured_outputs=True, act_without_confirmation=True, tool_selection=all, log_traces=True`.
- **Loop**: thread pool over tasks (`inference.py:334`). Each task runs `run_agent` (ReAct, `agent.py:423`) or `run_agent_structured` (`agent.py:539`) with `temperature=0`, `max_iterations=20`, `max_execution_time=600s` (checked only at the start of each iteration). If the limit is hit, output = `AGENT_STOPPED_MESSAGE` and it is recorded as an error.
  - *ReAct*: the system prompt holds all tool descriptions (`build_system_prompt`). Every step sends a **single user message** `task + "\n\nThought:" + scratchpad` (the history is re-sent and grows). `parse_action` (`agent.py:182`) takes the first ```json block, or the first `{"action":` brace-balanced object. If neither is found, the **whole reply is treated as Final Answer** and the task ends. Bad JSON gives a `PARSE_ERROR` observation and the loop continues.
  - *Structured*: native `tools=` schemas. Dotted names are sanitized to `_` (`agent.py:518`). The system prompt is only the datetime prefix (+ the act-without-confirmation suffix). A reply with no `tool_calls` is the final answer. **Several tool calls per request are allowed.** `json.loads(arguments)` (`agent.py:257`) is not guarded, so malformed arguments raise and **fail the whole task** (not retried).
- **Requests per task**: 1 LLM request per iteration, so ReAct ≈ (#tool calls + 1 + #parse errors) and structured ≤ that. The hard cap is 20 plus retries. (Inferred) committed 2026 runs average 2.5–4.1 tool calls per task (GT averages 1.37 actions), so expect **~3–5 requests per task, ~2.5–3.5k per model for all 690 tasks, worst case 13.8k**. ReAct prompt tokens grow roughly quadratically with steps.
- **Outputs**: `data/results/{domain}/{model_name}_{tool_selection}_{YYYY-MM-DD_HH-MM-SS}.csv` (QUOTE_ALL, columns `task,function_calls,full_response,error`, rewritten after every finished task, sorted by input row). Optional `..._traces.json` (`[{task, steps:[TraceStep]}]`, `ensure_ascii` default). `..._meta.json` is written at the start and again at the end. `domain` = tasks filename stem with `_tasks_and_outcomes` removed (`inference.py:289`). Inference also prints metrics using `--tasks_path` itself as GT (`cli.py:69-81`).
- **`_meta.json` fields** (`inference.py:226-246`): `model_name, model_id, provider, base_url, supports_temperature, tool_selection, tasks_path, ground_truth_version` (always the constant `"v2"`, **whatever `--tasks_path` is**), `num_tasks, num_to_run_this_invocation, num_resumed_from_prior_run, workers, log_traces, act_without_confirmation, structured_outputs, datetime_prefix, sample_system_prompt, started_at, finished_at`.
- **`--resume`**: picks the lexicographically latest `{model}_{tool_selection}_*.csv` in the same `data/results/{domain}/` (`inference.py:159`). Prior rows are keyed **by task text** (`:177`). Rows with an empty `error` are kept and the rest are re-run, in the same file.

## 3. Evaluation (`workbench-evaluate` → `src/cli.py:84`)
- **Flags**: `--tools` (repeatable; domain names, default all 6), `--models` (repeatable, default the whole registry), `--print_errors`, `--all_tools`. **Gotcha**: without `--all_tools` it looks for `*_domains_*` files (`metrics.py:274`). For our `all` runs you must pass `--all_tools`.
- **Pipeline**: `get_latest_results_path` (`metrics.py:259`) takes the latest `data/results/{tool}/{model}_{sel}_*.csv[.gz]`. It reads the GT version from `_meta.json` (`ground_truth_version_for_results` `:49`): no sidecar → `v1`; key missing → `v2`. `ground_truth_path(tool, version)` (`:66`) builds the path `data/processed/tasks_and_outcomes/[{version}/]{tool}_tasks_and_outcomes.csv`. **The meta's `tasks_path` is ignored.**
- **Matching (CRITICAL)**: `compute_metrics` (`metrics.py:152-163`) does `predictions.merge(ground_truth, on="task")` and **asserts** `len(pred)==len(gt)==len(merged)`. Results are matched to GT **by exact task text, not by row index**. A Bangla results file scored against English GT merges to 0 rows and raises an AssertionError.
- **Scoring** (`src/evals/evaluation.py`): `is_correct` (`:171`) runs the predicted and GT call strings on a fresh sandbox (`actions.py:65`, AST-parsed and allow-listed). It lowercases every column except `status, list_name, board`, then compares the 5 mutable tables as unordered row sets. Either analytics chart end date is accepted. Any `error` makes the task incorrect. `has_side_effects` (`:203`): the prediction changed `calendar_events/emails/project_tasks/crm_data` (not plots) **and** is not correct. `exact_match` is reported but not used for accuracy.
- **Output**: logs Accuracy % and Side effects % per model. With `--print_errors` it also prints per-task errors and the error categories. Nothing is written to disk (`scripts/evals/export_item_level_results.py` writes `data/results/item_level_results.csv.gz`).
- **Custom/single file**: `uv run python scripts/evals/calculate_metrics_for_single_file.py --predictions_path <results.csv> --ground_truth_path <any _bn.csv with task+outcome>` works directly (still merges on `task`). `workbench-evaluate` only works if `data/processed/tasks_and_outcomes/{domain}_tasks_and_outcomes.csv` exists for the results' domain dir. (Inferred) Naming a Bangla file `email_bn_tasks_and_outcomes.csv` gives results under `data/results/email_bn/`, which `workbench-evaluate --tools email_bn --all_tools` scores against that same file, as long as it sits in the top-level GT dir. A name like `email_tasks_and_outcomes_bn.csv` gives domain `email_bn` with no GT file.

## 6. Gotchas for Bangla task text
1. **Matching by task text** everywhere: the eval merge, `--resume`, and the trace lookup. The Bangla GT CSV must have the same `outcome` column and **unique** translated `task` strings, and its text must be byte-identical between the inference input and the GT used for scoring (watch Unicode normalization and trailing whitespace).
2. `ground_truth_version` is hard-coded `"v2"`. `workbench-evaluate` resolves GT from the **results dir name**, not from `tasks_path` (see §3 naming trick, or use `calculate_metrics_for_single_file.py`).
3. CSVs are read with pandas' default UTF-8. A BOM from Excel/Sheets (`utf-8-sig`) makes the header `﻿task`, which raises KeyError. Write with `encoding="utf-8"` and `quoting=csv.QUOTE_ALL`. Tasks contain embedded `\n`. A `\r\n` introduced by editors breaks matching of the literal email body (newlines are escaped but `\r` is not normalized, `metrics.py:166`).
4. Outcomes contain **English literals copied from the task**: quoted email bodies and subjects, event and task names, board names, and person names. The directory lookup is a substring match on Latin emails (`company_directory.py`), and `search_emails` uses English keyword matching. Keep quoted literals, names, emails and IDs in their original English/Latin form when translating. Otherwise a correct model still fails.
5. The ReAct parser and prompts are English-specific. `action == "Final Answer"` must be exact. A reply with no JSON block is treated as the final answer (an early silent stop). The scaffold uses "Thought:"/"Observation:". `wrong_email`/"Didn't follow REACT" are English-agnostic heuristics.
6. `json.dump` traces use ASCII escapes (`\uXXXX`). They are valid but unreadable without `ensure_ascii=False`. `open()` is called without `encoding=` (`inference.py:155,183,248`). That is fine on macOS/Linux UTF-8 locales (inferred).
7. Analytics/calendar dates in tasks ("November 1", "tomorrow") are resolved relative to 2023-11-30. Translated dates must stay unambiguous.

## 7. Our patch (bangla-eval)

- **What changed**:

    - `groq`: `https://api.groq.com/openai/v1`, key `GROQ_API_KEY`, URL override `GROQ_BASE_URL`.
  - If the key is missing for a provider with no fallback, `resolve_route` raises `OSError("Missing required environment variable 'OLLAMA_API_KEY'…")`.
